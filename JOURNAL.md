## 2026-07-30 — Documented the Podman-over-Docker rationale (retroactively, no re-litigation)

User asked why Podman was chosen for Open WebUI/Open Terminal over Docker; no prior journal entry recorded an explicit decision, so it was never actually debated in-session - Podman was simply the starting choice both container scripts were built on (`start-open-webui.sh`, `start-open-terminal.sh`, see SETUP.md). Capturing the reasoning now so it isn't lost:

- **Fedora default**: Podman ships as Fedora's default container engine; Docker isn't installed out of the box, so Podman was the path of least resistance rather than an extra package to add.
- **Rootless by default**: both containers already run rootless, consistent with the general footprint/privilege-conscious posture used elsewhere (the `slim` image tag, loopback-only binding for `open-terminal`'s port 8000).
- **No daemon**: Podman's fork-exec model means no long-running root `dockerd` on a box that's also serving an LLM and is reachable over Tailscale - smaller attack surface than a persistent root daemon.
- **Docker-CLI compatible**: the scripts use standard Docker-style flags (`--network host`, named volumes, `-p 127.0.0.1:8000:8000`) under `podman run`/`podman start`, so there was no real switching cost versus Docker.

No action taken - this is a documentation-only entry, nothing about the running containers changed.

## 2026-07-30 — Added a second, uncensored model (`start-qwen3-uncensored.sh`) after ruling out Gemma as fixable and Qwen3.5 as unusable

Went looking for a Gemma 4 E4B replacement after concluding its extra crash/hang frequency (beyond the shared iGPU fence-timeout bug, see entries below) wasn't worth chasing further now that vision isn't a hard requirement. Investigation, in order:

**Ruled out swapping models to fix crashes.** The underlying `i915`/Vulkan fence-timeout hang hit Qwen3 first (2026-07-28, 17:44 entry) and again just yesterday (the "third llama-server drop," this same 2026-07-30 entry below) - it's a shared iGPU/Vulkan-backend issue, not something a different model sidesteps.

**Ruled out Qwen3.5-4B as a "same family, newer" option.** Checked `ggml-org/llama.cpp#21831` directly - still open, and now confirmed affecting Qwen 3.5-35B and Gemma-4-26B too on newer builds. It's a general hybrid/recurrent-memory (SWA+SSM) cache-restore-selection bug, not specific to the 4B checkpoint that was already ruled out here on 2026-07-26.

**Explored uncensored/abliterated models for a separate, blunt-assistant-role third server** (explicitly not meant to carry agent/tool-calling duty like production Qwen3). Checked the UGI Leaderboard (`huggingface.co/spaces/DontPlanToEnd/UGI-Leaderboard`, a live Gradio Space - had to drive it via actual browser automation, WebFetch can't render it) for real, dated data instead of trusting the wave of SEO-blog content this topic attracts. Initial pick (`mlabonne/NeuralDaredevil-8B-abliterated`, Llama-3 8B, verified real via the leaderboard) was correctly pushed back on for being from 2024. Re-searched filtered to the exact base already proven stable here (`Qwen3-4B-Instruct-2507`) and found several current abliterated variants; picked **`arnomatic/Qwen3-4B-Instruct-2507-heretic-av2`** (abliterated via the "Heretic" tool, Apache 2.0, refusals 19/100 vs 100/100 base per its own model card) - highest UGI (38.81) and NatInt (17.77) of the same-base options, tested as recently as 2026-01-02, and scores *higher* NatInt than the untouched base (13.76).

**Why this specific pick de-risks integration**: same architecture/chat template as production Qwen3, so it inherits neither Gemma's bespoke `chat_format:peg-gemma4`-style parser bugs nor the Qwen3.5 hybrid-memory cache bug - it goes through the same generic-autoparser tool-calling path already proven on this exact `llama.cpp` checkout.

**Set up (`start-qwen3-uncensored.sh`, new script)**: GGUF from `mradermacher/Qwen3-4B-Instruct-2507-heretic-av2-GGUF` (Q4_K_M, ~2.6GB, "fast, recommended" per the quantizer) - mradermacher is a well-established quantizer, not a random reupload. Carries over both fixes already proven necessary for this exact base model: `--reasoning off` (shared-template reasoning-branch bug) and `GGML_VK_MAX_NODES_PER_SUBMIT=1` (iGPU fence-timeout mitigation, backend-level not model-specific). Bound to **port 8081** (production stays on 8080) so it can run standalone or alongside production.

**Not yet done**: this model has *not* been run through the same validation gauntlet as production Qwen3 (multi-turn `cached_tokens` growth check, real Open WebUI tool-declaration payload test) - it wasn't required since its role is a blunt/direct assistant, not agent-mode duty, but re-verify before ever promoting it to that role.

**Download hit real friction worth remembering**: the first `curl` attempt crawled at ~32KB/s despite a 200mbps connection - HF's CDN throttling that single stream, not a local bandwidth problem. Adding a browser-like `-A` User-Agent got it to ~600KB/s-1.2MB/s, still well under line speed but workable. A background watcher script written to detect "has curl exited" via `pgrep -f "<the curl command text>"` had a self-matching bug - the watcher's own invocation contained the search pattern as literal text, so it matched itself and looped forever even after the real curl process died from a connection reset. Fixed by tracking the actual PID (`kill -0 $PID`) instead of pattern-matching command text - the more robust way to watch a specific background process going forward.

**Verified working post-download**: GGUF magic bytes checked, server starts clean, `/health` OK, real chat completion returns `finish_reason:"stop"` (no reasoning-branch hang) at 11.58 tok/s generation / 34 tok/s prompt processing - confirms genuine Vulkan/iGPU execution, not a silent llvmpipe (CPU) fallback.

**Checked combined memory footprint before running both models at once, decided against it for now**: `start-qwen3.sh`'s own comment documents ~6GB Vulkan-visible for one Qwen3-4B instance at `-c 24576`; two such instances (production + this one, both at the same `-c`) would be ~12GB combined, over the documented ~7.4-9.8GB budget. Decided to run the two mutually exclusively (same pattern as Qwen3/Gemma sharing port 8080 today) rather than shrink context and risk adding memory pressure while the i915 fence-timeout/GPU-hang issue is still unresolved. `start-qwen3-uncensored.sh` updated to document this reasoning. Revisit concurrent use later if the context is shrunk (e.g. `-c 4096` for this model, roughly halving its footprint) and the GPU-hang situation stabilizes.

**Wired the uncensored model into Open WebUI too, without weakening the mutual-exclusivity decision above**: rather than reconfigure Open WebUI's connection every time the active `llama-server` changes, updated `start-open-webui.sh` to use the plural `OPENAI_API_BASE_URLS`/`OPENAI_API_KEYS` env vars (semicolon-separated, a real documented Open WebUI feature - confirmed via `docs.openwebui.com/reference/env-configuration` before using it) to register both `http://localhost:8080/v1` (production) and `http://localhost:8081/v1` (uncensored) as connections at once. Only one `llama-server` process actually runs at a time either way; whichever port is down just shows as unreachable in the model picker instead of erroring. Recreated the `open-webui` container to pick up the new env vars (safe - its data lives in the separate `open-webui-data` named volume, untouched by container removal). Verified via `podman inspect` that both URLs landed correctly and via container logs that nothing errored on startup.

**Real-use testing turned up two distinct problems, only one of which is fixable by config.** Tested with a system prompt aimed at reducing hedging/refusals on sensitive-but-legal topics (lockpicking mechanics: answered fully and directly both with and without the system prompt - abliteration alone already handles this category, so that particular test couldn't show whether the system prompt itself does anything). Two real findings from further testing:
1. **A long-form creative-writing request degenerated into a cycling phrase loop** (a short clause repeating with minor variation, never reaching a natural stop). Root cause: no anti-repetition sampling and no generation-length cap were set at all - `--repeat-penalty`/`--repeat-last-n` were both left at defaults (disabled / 64-token window) and `-n`/`--n-predict` defaults to `-1` (infinite) in this build, so a small 4B model falling into a repetition attractor during sustained long-form generation had nothing stopping it short of the full `-c 24576` context.
2. **A factual question about a niche real-world media property got a fully confabulated answer** - fabricated a nonexistent TV adaptation, wrong premise, wrong creator/character relationship, with a false specific detail (a fake premiere date) making it sound more authoritative than it was. This is a hallucination/knowledge-grounding limitation, not a censorship or config issue - not fixable by sampling tuning or system prompt. Noted as a hard scoping boundary: this model is for blunt conversation/creative writing/direct engagement on sensitive-but-legal topics, not a reliable source for real-world facts, especially niche ones.

**Fixed the repetition/runaway issue (problem 1) in `start-qwen3-uncensored.sh`**, confirmed via `llama-server --help` for this exact build before adding anything (flag names/behavior can vary across versions):
- `--repeat-penalty 1.1 --repeat-last-n 256`: standard token-frequency penalty, window widened from the 64-token default to actually cover longer-range repeats like the one observed.
- `--dry-multiplier 0.8` (base/allowed-length left at defaults 1.75/2): DRY sampling penalizes repeated *phrase* sequences specifically - a better match for what actually happened than plain repeat-penalty alone.
- `-n 2048`: hard ceiling on tokens per response - the guaranteed backstop regardless of whether the two penalties above catch a given loop.

**Verified empirically, not just via `/props`**: `/props` reported `repeat_penalty`/`repeat_last_n`/`dry_multiplier` correctly but showed `n_predict: -1` despite `-n 2048` being passed - looked like the cap wasn't taking effect. Confirmed via a real generation test (a "write an extremely long story, don't stop early" prompt) that it actually is enforced: response came back with `finish_reason:"length"` and `completion_tokens:2048` exactly, cut off mid-sentence as expected. So `/props`'s `n_predict` field is a cosmetic reporting bug in this build, not a real gap - worth remembering if it comes up again rather than re-debugging from scratch.

## 2026-07-29 — Wired up Open Terminal (open-webui/open-terminal) as an Open WebUI Integration

Added shell/file access for the chat models via `open-webui/open-terminal`, a small self-hosted remote-shell API upstream ships specifically as an Open WebUI Integration (Admin/personal Settings → Integrations → Open Terminal — a first-class feature, not a generic OpenAPI tool server).

**Deployment (`start-open-terminal.sh`, new script, mirrors `start-open-webui.sh`'s idempotent podman pattern)**: rootless Podman container, `slim` image tag (~430MB Debian base) rather than `latest` (~4GB full toolkit) or `alpine` — consistent with the mmap-not-mlock, mind-the-footprint posture already used for the llama.cpp scripts on this 16GB box. Named volume (`open-terminal-data` at `/home/user`) for persistence, matching `open-webui-data`'s pattern.

**Networking deliberately differs from `start-open-webui.sh`**: that script uses `--network host` (required so the container can reach llama-server's loopback-only `127.0.0.1:8080`). Open Terminal has no such requirement — Open WebUI's backend proxies all requests to it, so upstream docs say it only needs to be reachable from the host, not the LAN. Used `-p 127.0.0.1:8000:8000` on ordinary bridge networking instead: publishing to loopback only is a network-level guarantee regardless of what address the app binds to inside the container (unlike trying to control it via an unconfirmed `OPEN_TERMINAL_HOST` env var). Rationale for treating this more conservatively than the chat UI's port 3000: 3000 has `WEBUI_AUTH`'s login page in front of it before anyone reaches a model; a raw shell API's only gate is the API key, so it doesn't get the LAN-reachable tradeoff extended to it by default.

**API key**: generated with `openssl rand -hex 32`, stored at `~/.config/open-terminal/api-key` (`chmod 600`, dir `chmod 700`) — read by the start script at container launch, not hardcoded in it.

**Open WebUI side**: found a pre-existing "my terminal" integration entry already configured (from earlier user experimentation, per chat history) pointed at the wrong port (`http://localhost:3000`, Open WebUI's own port, producing a "Failed to connect" toast) with a stale API key. Fixed the URL to `http://localhost:8000` and replaced the key via clipboard (`wl-copy` — Wayland session) rather than pasting the raw secret through chat/tool-call text, then cleared the clipboard after. Verified end-to-end via the actual UI: Files panel lists the container's home directory, and the Terminal panel shows a live connected shell (`user@<container-id>:/app$`).

**Not yet done**: no `OPEN_TERMINAL_PACKAGES`/`_PIP_PACKAGES`/`_NPM_PACKAGES` configured (slim image ships git/curl/jq only) — add if a specific workflow needs more. Not ported to Windows (no Podman there, same as Open WebUI itself).

**End-to-end chat test uncovered a second, more interesting bug**: asking Qwen3 to run `uname -a` via the terminal integration failed with `Terminal unavailable: Terminal server 'http://localhost:8000' not found`, traced (via `podman logs`, then reading `open_webui/utils/tools.py`'s `get_terminal_tools`) to Open WebUI having **two independent terminal-connection stores**: a personal "Direct" one (`user.settings.ui.terminalServers`, used only by the Files/Terminal side panels — client-side, no backend involvement) and a system-level one (`Config` key `terminal_server.connections`, an admin-only list with real `id` fields, which is what the chat/tool-calling backend actually resolves `terminal_id` against). The personal entries have no `id` field at all, so when a chat request passes the connection's URL as `terminal_id` (falling back since there's no id), the backend's `next(c for c in connections if c.get('id') == terminal_id)` lookup against the (empty) admin list never matches. The Settings UI's personal "Add Terminal Connection" dialog has no path to populate the admin-level list, and the corresponding admin UI page isn't linked from the settings sidebar despite the backend routes (`/api/v1/configs/terminal_servers`) existing — added the connection directly via `fetch()` in the browser's own JS console context (reusing the logged-in session, `crypto.randomUUID()` for the id) rather than hand-authenticating a curl call. Once a matching admin-level entry existed, selecting it from the chat composer's "SYSTEM" category (as opposed to "DIRECT") worked.

**Also hit, and unstuck, a recurrence of the Qwen3 tool-call hang from earlier today (issue #6 above)**: first real attempt through chat hung with `/slots` showing `is_processing:true`/`has_next_token:false` at `n_decoded:39` — same "stuck in the `peg-native` response formatter" signature, this time triggered by the terminal tool's schema rather than Builtin Tools. `llama-server` didn't respond to `SIGTERM`; killed with `SIGKILL` and relaunched via `start-qwen3.sh` (confirmed with the user first, since it's the actively-running production server). The retry succeeded cleanly — real `run_command` → `get_process_status` tool-call round trip, correct `uname -a` output surfaced in the final answer — so this looks like an intermittent occurrence of the same underlying parser bug rather than something newly broken by the terminal integration, but it's a data point that any tool-schema addition (not just Builtin Tools) can trigger it.

**Browser-automation note, not project-specific but worth remembering**: clipboard paste (`wl-copy` + synthetic `ctrl+v` via Chrome DevTools Protocol) into these connection-key fields was highly unreliable — silent no-ops, and on two occasions old + new clipboard contents got concatenated into the field instead of replacing it. ## 2026-07-29 — Open WebUI tuning for Gemma 4 E4B, then switched production to Qwen3-4B-Instruct-2507 for working agent mode

Started from a simple question ("what are Open WebUI's defaults, what's optimal for Gemma on this hardware") and ended up finding and fixing a real root cause of the crash-avoidance problem, then discovering Gemma can't actually do agent mode reliably on this build and switching the production server to Qwen3 instead.

**Initial conservative pass on `start-gemma-e4b.sh`**: dropped `-c` from 16384 to 4096 and disabled `--mmproj` (vision) to reduce memory pressure while the 2026-07-28 fence-timeout mitigation (`GGML_VK_MAX_NODES_PER_SUBMIT=1`) was still unconfirmed. Also disabled Open WebUI's Title/Follow-Up/Tags auto-generation and Web Search in Admin Settings → Interface (Autocomplete Generation and Web Search were already off).

**`-c 4096` immediately failed in real use**: first real Open WebUI message hit `request (5177 tokens) exceeds the available context size (4096 tokens)`. Raised to `-c 8192`, which cleared it — but this pointed at something producing ~5100 tokens of overhead on every message regardless of content, worth actually tracing rather than just padding context further.

**Traced the real request two ways**: (1) `llama-server --log-prompts-dir` to capture the literal formatted prompt hitting the model, (2) a `window.fetch` hook injected into the Open WebUI tab via `javascript_tool` to capture the literal JSON body leaving the browser. Found:
- Open WebUI's own architecture: `POST /api/chat/completions` returns instantly with just `{status, task_ids, chat_id}` — the actual token stream arrives over a separate persistent Socket.IO WebSocket (`/ws/socket.io/`), not the HTTP response. Confirmed by reading raw `chat:completion` event frames out of a DevTools HAR export from `~/Downloads`.
- The 5100-token overhead was **33 native "Builtin Tools" declarations** (Knowledge Base, Memory, Notes, Tasks, Automations, Calendar, Chat History, Time/Date) that Open WebUI auto-attaches to *every* request when a model's Capabilities → Builtin Tools is on — completely independent of whether the user's message needs any of them. One measured "test" message: 172.1s prompt processing (5164 tokens) + 36.2s generation (191 tokens) = ~208 seconds total, final answer just "I'm not sure what you'd like me to do."
- Disabling Builtin Tools for the Gemma model entry (Admin → Models → Capabilities) dropped that same class of message to 174 prompt tokens.
- Open WebUI's Title/Follow-Up/Tags Generation toggles exist in **two separate places** that don't sync: Admin Settings → Interface (site default) and personal Settings → Interface (per-account, silently overrides the admin default). Disabling only the admin copy left `background_tasks: {title_generation: true, ...}` still true in the actual outgoing request — had to disable both.

**The user added `</nothink>` to the model's System Prompt field trying to suppress Gemma's visible reasoning.** Confirmed via the model settings page and via prompt trace that this does nothing — Gemma's `<think>...</think>` behavior here is `llama-server`'s own `--reasoning-format`/`chat_format:peg-gemma4` parser convention, not a model-native control token the way Qwen3 respects `/no_think`. The actual fix is the server flag `--reasoning off` (or `--reasoning-budget 0`), added to `start-gemma-e4b.sh`. Cleared the stray system prompt text.

**Update, 21:58 - likely root cause found (not just the crash symptom) via upstream research.** Pushed back on "we still don't know why this actually happens" - the two patches above only change how the server fails, not why the iGPU's fence times out at all. Searched for prior art: `i915`/Vulkan-compute fence timeouts on integrated GPUs turn out to be a recognized class of bug, not something specific to this machine - multiple open `llama.cpp` issues describe the same `Fence expiration time out` -> `GPU HANG` -> `vk::DeviceLostError` chain on other Intel iGPU generations (Meteor Lake, Arrow Lake, Arc iGPU: [#20201](https://github.com/ggml-org/llama.cpp/issues/20201), [#16684](https://github.com/ggml-org/llama.cpp/issues/16684)).

The most useful match was [#21724](https://github.com/ggml-org/llama.cpp/issues/21724) - an **identical failure chain on an AMD APU** (Renoir gfx90c, also integrated/shared-memory), with a validated root cause: the Vulkan backend batches up to 100 compute-graph nodes into a single GPU submission (`ggml-vulkan.cpp`, `max_nodes_per_submit`); on an integrated GPU this accumulated work can take long enough that it exceeds the kernel driver's hang-detection timeout (AMD's `amdgpu.lockup_timeout`, i915's fence-expiration equivalent here), and the kernel resets the GPU thinking it's actually stuck - a false-positive hang, not a real one. The validated fix there was reducing the per-submission node count to 1.

Checked this checkout's `ggml-vulkan.cpp` (line 6176-6182): `GGML_VK_MAX_NODES_PER_SUBMIT` already exists as an env var (default 100, the same default that caused the AMD crashes), no rebuild needed to test it. **Set `GGML_VK_MAX_NODES_PER_SUBMIT=1` in `start-gemma-e4b.sh`** (exported before the `exec`, commented with the reasoning and the upstream issue link) and restarted. Quick check: generation speed unaffected (8.05 predicted tok/s on a short completion, in line with the ~9-9.8 tok/s documented baseline) - matches the AMD issue's own finding of no performance penalty from this change.

**Update, 22:03 - user asked "check now realtime, got timeouts" - investigated, found the alert log was stale again, but turned up a real third bug.** `gpu-fence-watch.service` had restarted *again* (22:00:22) and replayed old PIDs (20696, 22242, 24258, 25063) into `gpu-fence-alerts.log` as duplicates - none of that was new. Cross-checked with the raw kernel ring buffer (`dmesg -T`, immune to journald's replay issue since it reads the kernel's own buffer directly) - zero fence lines in the current window. So no evidence the fence timeout itself recurred since the mitigation went live.

However, found a genuinely new, real crash: PID 25063 (running with both crash-patches, but *without* the node-per-submit mitigation - that only applied to the next restart) hit a real device-lost error at 21:54:04 (visible in Open WebUI's own error log), survived it thanks to the patches, then **crashed anyway at 21:58:16 when I sent it SIGTERM to restart for the mitigation test** - a coredump, not a graceful shutdown. Backtrace: `llama_context::~llama_context()` -> `ggml_backend_vk_free` -> `ggml_vk_cleanup` -> `ggml_vk_synchronize` - the *shutdown* path also makes an unguarded Vulkan call ("wait for any pending command buffers to finish" before freeing), and once the device is already lost, that throws too, uncaught, straight out of a destructor. A **third** unguarded call site, this time not in request handling but in teardown - meaning any restart of an already-broken server (which is exactly the recovery procedure used all day) could itself crash instead of exiting cleanly.

**Patched `ggml_vk_cleanup()` directly** (`ggml/src/ggml-vulkan/ggml-vulkan.cpp`, line ~15410) - wrapped its `ggml_vk_synchronize(ctx)` call in `try { ... } catch (const vk::SystemError& e) { GGML_LOG_WARN(...); }`, matching this file's own existing exception-handling convention (`catch (const vk::SystemError& e)` is already used at several other call sites in the same file). This is backend-level code (not server-specific), so the fix benefits any consumer of `ggml-vulkan`, not just `llama-server`. Rebuilt, restarted - ended up with two `llama-server` processes briefly (the `pkill` in the restart sequence didn't actually kill the prior one; cleaned up manually, confirmed via `ss -tlnp` which PID actually held port 8080). Verified generation still works post-patch (`Paris`).

**Current state, 22:03: three local patches + one trial mitigation, all active on PID 28220:**
1. `tools/server/server-context.cpp` - `server_slot::prompt_save()` catches device-lost instead of crashing.
2. `tools/server/server-task.cpp` - `server_prompt_cache::load()` catches device-lost instead of crashing.
3. `ggml/src/ggml-vulkan/ggml-vulkan.cpp` - `ggml_vk_cleanup()` catches device-lost during shutdown instead of crashing.

All three patches are local-only, unsubmitted, will not survive a `git pull`.

**This is a trial, not a confirmed fix** - the fence timeouts are intermittent (roughly hourly during real use, per today's 4-5 confirmed occurrences), so this needs real usage over a comparable window to know if it actually reduces/eliminates them, not just a synthetic smoke test.
