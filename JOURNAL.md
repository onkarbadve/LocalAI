## 2026-08-20 — GPU hang investigation (Aug 19) + EAGLE3 speculative decoding retest

**Goal**: root-cause the hard-poweroff-requiring hang from the previous session, then retry the EAGLE3 speculative decoding attempt that had triggered it.

**Investigation — the Aug 19 "GPU hang"**:
Journal/kernel logs (`journalctl -b -2`, boot spanning Aug 16 20:09 → Aug 19 18:27) show this was **not** a GPU driver fault — no `i915`/`drm` error, reset, or TDR was ever logged, and `pstore`/`abrt` have no crash artifacts. What happened:
- **18:04:15** — kernel OOM-killer fires, kills a `python3` process (PID 133437, 8.2GB virtual / 4.48GB RSS) running in a konsole tab. `Free swap = 4kB` at that instant — the 8GB of swap is `zram` (compressed swap living *in* RAM, not disk); the OOM dump shows ~4.5GB of the 16GB RAM was consumed just holding compressed swap pages. Model tensors compress poorly, so the "8GB swap" bought far less real headroom than it looked like.
- The ~34 `Purging GPU memory, 0 pages freed, 0 pages still pinned` lines right after are a side-effect of the OOM notifier firing (pinned count was 0, pool ~25MB — compositor-sized, not workload-sized), not an independent GPU lockup.
- **18:04–18:23** — the single OOM kill didn't fully relieve pressure. `kwin_wayland` logs escalating input-lag warnings (timer events up to 4s late, "your system is too slow"), `polkitd` hits a 10s spawn timeout at 18:19:54 — the desktop was thrashing on memory, not instantly frozen.
- **18:23:02** — last kernel/desktop log line. `tailscaled` (less GPU/interactive-path dependent) keeps logging until 18:27:34, then the boot record ends — hard poweroff followed sometime after.
- Checked 3 other retained boots with `crash`-tagged endings (`-9`, `-8`, `-7`) for the same OOM+purge signature: none matched. Looks like a one-off overcommit, not a standing config problem.

**Root cause, once traced to the actual work**: the Aug 19 JOURNAL entry only documented a FastDraft/Phi-3-mini speculative-decoding test, but the box was actually also mid-attempt on **real EAGLE3** — `models/Qwen3-8B_eagle3-int8-ov` (int8, 2.0GB draft head) was written at 17:59:38, 5 minutes before the OOM. That attempt paired the EAGLE3 draft head against `Qwen3.5-9B-int4-ov` as target while `ovms-qwen3.5-9b-text.service` was likely still resident with the same 9B model — two copies of ~9B-class weights plus a draft head pushed the 16GB UMA box past its budget.

**The pairing was also wrong, independent of memory**: `Qwen3-8B_eagle3-int8-ov`'s config (`hidden_size=4096`, `vocab_size=151936`, `draft_vocab_size=32000`, single decoder layer) matches `Qwen3-8B-int4-ov` (`hidden_size=4096`, `vocab_size=151936`) exactly. `Qwen3.5-9B-int4-ov` has `vocab_size=248320` — a different tokenizer family. EAGLE3 draft heads consume the target's hidden states directly, so `Qwen3-8B` was always the correct target for this draft head, not `Qwen3.5-9B`.

**EAGLE3 retest, done safely**: `ovms-qwen3.5-9b-text.service` confirmed stopped first; ran under `systemd-run --user --scope -p MemoryMax=12G -p MemoryHigh=10G` so a runaway process would get cleanly OOM-killed instead of thrashing the desktop again. Target `Qwen3-8B-int4-ov` on GPU (4.6GB) + draft `Qwen3-8B_eagle3-int8-ov` on CPU (2.0GB) — comfortably under the ~10GB that was free. 64 tokens, greedy, 3 timed runs:

- **Baseline (GPU, no draft)**: **9.30 tok/s**
- **EAGLE3 (GPU target + CPU draft)**: **5.18 tok/s** (‑44%)

Output was coherent (not garbled), confirming the corrected pairing is architecturally valid. GPU+GPU draft variant not tested (FastDraft results from Aug 19 showed GPU-draft is worse than CPU-draft on this hardware — same bandwidth-contention mechanism would apply).

**Lessons**:
- On this Iris Xe UMA box, speculative decoding (FastDraft *and* now EAGLE3) is consistently net-negative on ≤9B-class models — draft/verify overhead and CPU↔GPU sync cost more than the saved forward passes, matching the existing [docs/lessons-learned.md](docs/lessons-learned.md) entry.
- `zram`-only swap gives much less real headroom under LLM/tensor workloads than its nominal size suggests (poor compression ratio) — don't treat "8GB free swap" as real slack when sizing concurrent model loads on this machine.
- A `systemd-run --scope -p MemoryMax=` cap around ad-hoc GPU/model-loading scripts is now the standard way to test anything that might overcommit memory on this box — it contained a process cleanly with no desktop impact.
- Verify draft/target `hidden_size` + `vocab_size` compatibility from `config.json` before loading either model, not after — would have caught the wrong pairing without spending any memory budget.

**Next steps**: none planned — EAGLE3 confirmed net-negative on this hardware for ≤9B models, same as FastDraft. Revisit speculative decoding only for larger/slower models per the existing lessons-learned guidance.

**Addendum, same session: Speculative decoding (FastDraft/EAGLE pipeline) evaluated on Intel Iris Xe.**

**Results (1 warmup + 5 timed runs, greedy decoding, 128 tokens max)**:
- **Baseline (GPU, No Draft)**: **`19.07 ± 0.06 tok/s`**
- **Speculative (GPU Main + GPU Draft, `assistant_tokens=5`)**: **`7.73 ± 0.01 tok/s`** (-59.5% slowdown)
- **Speculative (GPU Main + CPU Draft, `assistant_tokens=5`)**: **`8.82 ± 0.03 tok/s`** (-53.8% slowdown)
- **Draft token sweep (`num_assistant_tokens` on CPU draft)**:
  - `assistant_tokens=1`: **`12.27 tok/s`**
  - `assistant_tokens=2`: **`11.40 tok/s`**
  - `assistant_tokens=3`: **`10.91 tok/s`**

**Root cause / Takeaway**:
On a UMA iGPU architecture (Intel Iris Xe with shared ~40–50 GB/s system DDR5 memory bandwidth), speculative decoding is **strictly net-negative on small/fast base models (3B–4B)**.
1. `Phi-3-mini` is already fast (~19.1 tok/s baseline). The latency of executing the draft model iterations + synchronization overhead exceeds the latency saved during verification.
2. In UMA systems, the draft model and target model compete for the *same* physical memory bandwidth. Unlike dGPUs with massive memory bandwidth (where compute is cheap and memory read batching saves wall time), UMA bandwidth contention degrades sequential token speculation.
3. FastDraft/EAGLE requires strict tokenizer equivalence (`are_tokenizers_equal` assertion in `fast_draft_strategy.cpp`), prohibiting arbitrary cross-architecture drafting (e.g. Qwen2-0.5B draft with Qwen3.5-9B fails with mismatched tokenizer error).

**Next steps**: retain direct autoregressive generation on iGPU for models <10B; speculative decoding is only worth revisiting on very large/quantized models (e.g. 30B+ MoE) where baseline autoregressive token generation falls below ~2 tok/s.

**Addendum, same session: IPv6 prefix had actually changed since the 2026-08-18 firewall doc, and the "stable in practice" claim in that doc was wrong.** Following up on the ethernet/throughput checks, `ip -brief addr` showed the Pi's and Fedora laptop's global IPv6 now in `2406:b400:53:481::/64`, not the `2406:b400:53:1e77::/64` documented the day before — and the Pi's live nftables `input` chain still had `1e77` hardcoded, so the LAN-convenience IPv6 accept rule had gone stale (failed safe — link-local/Tailscale still worked, just not global-IPv6 LAN access). Dug through the Pi's journal (continuous ~3-day uptime spanning the change, boot `15d80b4a...` 2026-08-15 22:00 → 2026-08-18 22:40) to find the actual transition: a *third* prefix, `a692`, was live earlier that boot; `1e77` appeared alongside it around 2026-08-18 12:07 IST (both addresses present on `wlan0` simultaneously for a while — proves this wasn't a Pi reboot causing it, since the Pi didn't reboot at 12:07); then `1e77` was dropped and `481` appeared at 22:40:16, coincident with (but not necessarily caused by) a Pi reboot at that same timestamp. Root cause is upstream — ISP/router-side SLAAC prefix delegation rotating the `/64` subnet ID — not visible from either box's own logs, so the exact ISP mechanism (WAN reconnect vs forced DHCPv6-PD renewal) stays unconfirmed. All three observed subnet IDs (`a692`, `1e77`, `481`) share the same `/48` (`2406:b400:53::/48`), so that's the actually-stable unit.

**Fix applied**: Pi's `/etc/nftables.conf` (backed up first to `/etc/nftables.conf.bak-20260819`) — `ip6 saddr 2406:b400:53:1e77::/64 accept` → `ip6 saddr 2406:b400:53::/48 accept`. Validated (`nft -c -f`), reloaded (`systemctl reload nftables`), confirmed live in `nft list ruleset`, confirmed a **fresh** SSH session still connects post-reload (not just the existing session staying up), `nftables.service` still active. Also updated `docs/network-ipv6-setup.md` and `docs/overall-setup.md` to replace the hardcoded `/64` and the disproven "stable in practice" claim with the `/48`-is-stable finding.

**Also confirmed, no action needed**: `duckdns-update.timer` runs every ~3min and had already kept the public hostname (`aagaumulga.duckdns.org`) correct through the `1e77→481` transition (log-verified) — the public Caddy 80/443 path was never actually affected by any of this, only the LAN-convenience IPv6 rule was stale.

**Lesson**: a hardcoded IPv6 `/64` in a firewall rule is a hidden staleness trap on a connection where the ISP delegates a wider block (`/48` here) and rotates the `/64` within it — "written and verified same-day" doesn't mean "still true tomorrow" for anything sourced from upstream network state, same broader lesson as the 2026-08-18 continuation-audit entry but for infrastructure state instead of application config. When a value like this needs to go in a firewall rule, match on the widest unit that's actually been confirmed stable (via more than one observed rotation), not the narrowest unit that happened to be true at write-time.

**Addendum, same session: WiFi radio hard-disabled on the Pi, at user's explicit request against the codebase's own standing advice.** With `eth0` confirmed stable (this session's earlier checks), the user asked to disable the Pi's WiFi outright. This is specifically the action `99-eth0-wlan0-arbiter`'s own comments warn against — it deliberately avoids touching `nmcli radio wifi` because "a botched off/on already caused a real lockout earlier in this investigation" (the 2026-08-15 BSSID-pin incident chain). Flagged the risk and the existing automated design (arbiter already down-and-autoconnect-off's the `Badve` profile whenever `eth0` is up, so WiFi was already inactive; `wifi-watchdog.timer` provides an automatic fallback within ~4-8min if `eth0` ever drops) via a clarifying question; user chose the hard-disable option anyway, fully informed. Applied: `sudo nmcli radio wifi off` — persists across reboots. Verified: `nmcli radio wifi` → `disabled`, `wlan0` → `DOWN`, a **fresh** SSH session still connects, `ip route get` confirms egress via `eth0`.

**Important nuance, not a contradiction of the above**: checked `wifi-watchdog.sh`'s logic before applying — it only pings the *default gateway* (reachable via `eth0`), so it stays quiet as long as Ethernet works and won't fight this change during normal operation. But its own escalation ladder (step 4, at ~8min of gateway-unreachable) runs `nmcli radio wifi off/on`, which would flip the radio back **on** as an emergency recovery attempt if `eth0` ever fails too. That behavior was left untouched deliberately — it's the exact safety net the arbiter's comment references, and removing it wasn't asked for. So this WiFi-off state is durable during normal operation but not an absolute guarantee against the watchdog re-enabling it during a genuine `eth0` outage — that trade-off (no silent full lockout) was kept intentionally.

**Lesson**: when a user asks for the specific action a script's own comments flag as having caused a past incident, surface the documented risk and what's already mitigating it, then follow their explicit call once informed — don't silently refuse or silently comply. Checking the *current* interacting automation (the watchdog's actual trigger condition) before acting turned "this contradicts prior advice" into "this is safe under current conditions, with a known and load-bearing exception," which is a materially different and more useful thing to tell the user than the bare warning alone.

The next minute of `wifi-diag.log` told the real story: `16:48:22 signal=-34 gw_ping=3.27ms` (pre-pin, healthy) → `16:49:24 signal=-66 gw_ping=TIMEOUT` → `16:50:26 signal=-68 gw_ping=TIMEOUT` → `16:51:28 operstate=dormant`, i.e. the pin reproduced the exact wedge signature being investigated, within three minutes, plus 25% loss on a 20-packet test. Podman fix and Claude Code CLI install both stand and are verified.

**Problems**: two theories were wrong before the right one landed, both worth recording. (1) A self-recovering outage looked like a watchdog-triggered hard reset — the "no clean shutdown trace" evidence was real but the reboot turned out to be a user-initiated button press; the fresh-boot watchdog re-arm line is routine and is *not* evidence of a prior hang. (2) The community-consensus band-steering theory (mesh/smart-connect steering the Pi between 2.4GHz and 5GHz) was refuted by a live scan: the Pi was *already* on 2427 MHz, so `802-11-wireless.band bg` would have been a no-op. The real finding is that **two APs broadcast `Badve` on the same channel 4** — the ACT Archer C5 (`A8:29:48:64:35:5C`, signal 84, what the Pi was actually on) and the main router (`72:FA:C4:DB:EF:48`, signal 59) — so the trigger is an AP-to-AP BSS transition *within* one band, with co-channel interference making roaming decisions flappy. Identifying which BSSID was the main router needed a MAC-prefix match against the gateway's LAN MAC (`e4:fa:c4:db:ef:50`), since the BSSID is a locally-administered variant of the same base. Investigation was also badly slowed by the Pi flapping in and out of reachability throughout, and one attempt to delegate analysis to the Pi-side Claude Code instance failed outright — it's sandboxed to `/home/onkar` and can't read `/var/log` or run `journalctl` non-interactively.

**Lessons**: three, and the last is the expensive one. (1) "Already ruled out" flags from a previous session (power-save, undervoltage) are worth re-verifying live rather than trusting. (2) A plausible community consensus is still only a hypothesis — a single `iw dev wlan0 link` showing the current frequency refuted the band-steering story in one command and should have been the *first* check, before any theorising. (3) **A short ping immediately after a WiFi reassociation is not verification** — the link hadn't settled, and a 3-packet sample at 0% loss was reported as success one minute before the same link went to `TIMEOUT` and `dormant`. Verifying a WiFi change needs a sustained sample (20+ packets) *and* a look at the next few `wifi-diag.log` entries, not an instant snapshot. Corollary worth internalising: −66 dBm is a perfectly healthy RSSI, so "the main router is too weak" is the wrong diagnosis — with the Archer blasting −35 dBm **on the same channel 4**, the main router's carrier arrives ~31 dB down (~1000×) at the Pi's radio and gets desensed. RSSI was fine; SINR was destroyed. The tell is in the loss pattern: `rtt min 0.949ms` on a 25%-loss test means surviving packets are *fast*, which is co-channel interference, not path loss — pure range problems degrade latency, not just delivery. Candidate for [docs/lessons-learned.md](docs/lessons-learned.md).

**Follow-up same session — channel moved to 11, co-channel theory confirmed, pinning still abandoned**: the main router was moved to channel 11 (2462 MHz), leaving the Archer alone on ch 4, and the pin to `72:FA:C4:DB:EF:48` was retried with proper verification this time (40-packet ping + `wifi-diag.log` samples, behind a 10-minute armed rollback). Packet loss improved **25% → 5%**, confirming the near-far/co-channel diagnosis was right — but the link is still unusable: **−74 to −76 dBm with the radio rate-falling to 2.0 Mbit/s rx / 5.5 Mbit/s tx**, `gw_ping=TIMEOUT` samples, and a ~90s association delay during which the box was unreachable. Reverted → Archer at −35 dBm, 72.2 Mbit/s both ways, 30/30 packets 0% loss. Conclusion: the two APs differ by ~40 dB from the Pi's physical location and **no channel arrangement fixes that**. Net WiFi config change for the whole session remains zero. Useful metric note: `rx bitrate` is more decisive than RSSI — 2 Mbit/s rate-fallback is what actually proves a link unusable.

**RESOLVED from the console, same session.** The lockout was exactly the predicted stale-pin scenario: `nmcli -g 802-11-wireless.bssid connection show Badve` showed `6A:FA:C4:DB:EF:4F` still set — the transient rollback never ran, destroyed by the watchdog's own reboot as predicted. `sudo nmcli connection modify Badve 802-11-wireless.bssid ""` fixed it immediately. It was **not** a fresh radio wedge — `nmcli device wifi list` saw 7 SSIDs including `Badve` at full signal throughout the outage, so radio/scanning were healthy the whole time; a separate hotspot-connect failure during triage was just an empty post-boot scan cache, unrelated to the pin. Post-fix: 20/20 ping, 0% loss, 28.8/72.2 Mbit/s; watchdog's reboot cap fired exactly as designed (2 reboots that hour, then stopped escalating); all 9 containers were up the entire outage, unaffected. Lesson worth keeping: `nmcli connection up <profile>` failing "network could not be found" while the SSID is visible in a plain scan means check that profile's `802-11-wireless.bssid` before any other theory — it's a one-command diagnosis.

**Session had, for a period, ended with the Pi locked out — physical console required (now resolved, see above).** A third BSSID pin (`6A:FA:C4:DB:EF:4F`, the main router's 5GHz radio, which had just been measured at 130 Mbit/s and 0% loss during a deliberate Archer-off failover test) took the box fully offline; it did not self-recover after 30+ minutes, LAN and Tailscale both dark. Fix from a keyboard/monitor (or `Ctrl+Alt+F2`): `sudo nmcli connection modify Badve 802-11-wireless.bssid ""` then `sudo nmcli connection up Badve`. Powering the Archer back on does *not* help — a pin restricts the radio to that one BSSID and it will refuse every other AP. Likely cause: this router's BSSIDs are **locally-administered MACs** (`6A:`/`72:` are LA-bit variants of the real `e4:fa:c4:db:ef:50`), i.e. virtual addresses the router can regenerate, so a pin can silently become a pin to an address that no longer exists. Three pin attempts, three distinct failures — desense on 2.4GHz ch4, 2 Mbit/s rate-fallback on 2.4GHz ch11, total lockout on 5GHz ch157. **Conclusion: BSSID pinning is not viable on this router; the remaining levers are `roamoff=1` or ethernet.** Two flaws in the safety net were exposed and must be fixed before further WiFi work: `systemd-run --on-active` rollbacks are **transient and do not survive a reboot** (the watchdog's reboot fired in the same minute and can destroy the rollback before it clears the bad setting — use a real on-disk unit instead), and the watchdog **never clears a BSSID pin**, so it cannot recover from this class of lockout; that step belongs before the reboot step. The 2-reboots-per-hour cap did work as designed — no boot loop — but it also means the box stops trying and stays offline. Process lesson: two pin attempts had already failed and the recommendation on the table was to observe for a few hours before a third; that recommendation should have been restated as a risk rather than set aside on request.

**Also built this session — WiFi auto-recovery watchdog on the Pi** (`/usr/local/bin/wifi-watchdog.sh` + system `wifi-watchdog.{service,timer}`, enabled, every 2 min): pings the default gateway and escalates on consecutive failures — 2 → `nmcli connection up Badve`, 4 → `nmcli radio wifi off/on`, 6 → `systemctl restart NetworkManager`, 8 → reboot, capped at 2 reboots/rolling hour via a counter in `/var/lib/` (a `/run` counter would reset on reboot and so could never cap a loop). Ping success is ≥1 reply of 5, deliberately loss-tolerant so the degraded fallback AP doesn't get bounced. All six branches were verified before enabling via a sed-modified copy pointed at an unreachable gateway with the reboot call neutered. Read it with `journalctl -u wifi-watchdog -b`. This is the mitigation that should have been built at the *start* of the investigation — most of today's manual intervention would have been unnecessary.

**Late-session correction, from a handover doc written by a separate Claude session running locally on the Pi** (`/home/onkar/HANDOVER-pi-wifi-2026-08-15.md`, verified live): most of the AP-selection/pinning analysis above was answering the wrong question. Data across 3259 diagnostic samples shows **signal strength does not predict failure**; the real mechanism is the `brcmfmac` **scan engine wedging** (`wpa_supplicant: Failed to initiate sched scan` → stuck pending forever → `ssid-not-found`), not roaming or link quality. A reboot does **not** reliably clear it (confirmed: still wedged 18:37→19:02 across a watchdog-forced reboot). Outages are few and long (725/102/75/68/29/25/20 min ≥15min-episodes, the 725-min one alone ~67% of total downtime) rather than constant flapping, and that worst episode predates persistent journald's oldest surviving entry — its cause is genuinely unknown. Also: the watchdog being active during short ping tests invalidates them as loss-quality evidence (its own reconnect/reboot actions interleave with the test) — this applies to loss numbers recorded earlier in this same session, not only the local session's. `roamoff` needs `sudo` to read (`cat` unprivileged reads as unset even when live) and is now properly persisted via `/etc/modprobe.d/brcmfmac-roaming.conf`. **Direction changed as a result: ethernet is now the agreed fix**, user relocating the Pi to reach a port; a new `eth0-static` profile exists for this but currently conflicts with `Badve` — both hold `192.168.0.199/24` with autoconnect=yes, an unresolved ARP-conflict hazard confirmed live. **Do not boot with the ethernet cable attached until a NetworkManager dispatcher hook (proposed, not yet built) arbitrates between the two.** Knowledge was transferred to the Pi's own `~/.claude/CLAUDE.md` this session specifically so a local Claude Code session there has this context — worth doing on any future multi-machine investigation from the start, not after two sessions had already duplicated and partly contradicted each other's work.

**Next steps**: two extra reboots at 16:02:47 and 16:43:17 were briefly flagged as possible spontaneous reboots — **confirmed user-initiated**, so this box is *not* rebooting on its own and the WiFi line of investigation stands. The real fix for the near-far problem is a **router-admin action, not a Pi action**: move one of the two APs off channel 4 (main router to 1 or 11), which would make pinning to the main router actually viable. Pinning to the *Archer* (`A8:29:48:64:35:5C`, −35 dBm) is the other option that achieves the anti-roaming goal while keeping a strong link — and its DNS interception costs this box nothing functionally, since it intercepts port 53 from other clients and pollutes Pi-hole's client attribution, while Pi-hole's own upstream is DoT on port 853 and passes through untouched. `brcmfmac`'s `roamoff` param (confirmed present in `/sys/module/brcmfmac/parameters/`) remains the lever that targets the firmware wedge *mechanism* rather than the trigger. ## 2026-08-13 — Second Pi outage in 2 days (SSH unresponsive, manual reboot); actually fixed journald persistence this time

**Goal**: another full outage — SSH unresponsive, required a physical button reboot. Check logs for the cause, and find out why yesterday's "enable persistent journald" fix didn't leave any.

**Changes**: none for the crash itself — no root cause found, because (again) no logs survived. But fully root-caused *why the persistence fix didn't take*, which was three separate, stacked problems, not one:
1. Raspberry Pi OS ships a vendor drop-in, `/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf`, forcing `Storage=volatile` — this silently overrides a direct edit to `/etc/systemd/journald.conf` (drop-ins always win over the base file). Fixed by adding `/etc/systemd/journald.conf.d/10-persistent-storage.conf` (admin-tier, correctly outranks the vendor one) — but this alone still didn't work, see next.
2. journald has a boot-time flush gate: it only opens the persistent `/var/log/journal/<machine-id>/` journal after a flush is explicitly requested (normally done once, automatically, by `systemd-journal-flush.service` at boot) — restarting the daemon after changing `Storage=` mid-session does **not** retroactively trigger that flush, so it kept silently staying in `/run` (volatile) with no error or warning logged, even with the vendor drop-in fully removed as a test. Confirmed via `sudo journalctl --flush`, which forces it — `/var/log/journal/<machine-id>/system.journal` appeared immediately. `systemd-journal-flush.service` is enabled (`static`), so this step is a one-time manual unblock, not something that'll recur — the boot-time path was always going to work correctly once `Storage=persistent` actually won.
3. The Pi is at 88% disk usage (3.4G free of 29G) — below systemd's default `SystemKeepFree` floor (15%, ~4.4G), which would have made the persistent journal accept almost nothing or vacuum itself empty again. Set explicit caps in the same drop-in: `SystemMaxUse=200M`, `SystemKeepFree=300M`, `SystemMaxFileSize=50M`.

**Results**: verified live — `sudo journalctl --header` now shows files under `/var/log/journal/`, `sudo journalctl --disk-usage` reports 28.5M archived+active. Corrected the 2026-08-12 entry above in place (it asserted persistence was working; it wasn't) rather than just appending this correction on top, since the wrong claim there is what caused this to go undetected for a day.

**Separately, did manage to pin down the outage window itself** despite the missing system logs: Uptime Kuma's own SQLite heartbeat DB (`kuma.db`, not journald-backed, survived independently) showed all 8 monitored services going unreachable at 05:40:37 UTC (11:10 IST) with `connect ENETUNREACH 192.168.0.199:<port>` and staying down continuously (460 unbroken "down" heartbeats, no gaps) until the reboot at 13:21 UTC (~18:51 IST) — a 7h40m outage. `ENETUNREACH` to the host's own LAN IP from a `--network host` container means the *host* lost its route, not a container-networking artifact. The Pi's hardware watchdog (`RuntimeWatchdogUSec=1min` via systemd) never fired an auto-reboot across those 7.5 hours — if the kernel/PID 1 had truly hung, it should have self-recovered within ~1-2 min. That it didn't points to the kernel and systemd staying alive and responsive (still petting the watchdog) while specifically the network layer (NetworkManager/wpa_supplicant/interface) wedged and never recovered on its own. Root cause of *that* network-layer wedge is still unknown — this is a symptom pointer, not a fix.

**Problems**: burned real time on a wrong theory before catching it — assumed the fix was purely about `.conf.d/` file precedence/ordering (tried renaming the drop-in to sort alphabetically last, `zz-...`) before empirically testing (removing the vendor file entirely, which changed nothing) and realizing the actual blocker was the flush gate, unrelated to file ordering at all.

**Lessons**: **verify a config change actually took effect, don't just confirm the file was written** — yesterday's entry described the fix as done based on editing the file, not on checking `journalctl --header` for which directory it was actually using. That gap is exactly what erased this outage's logs too. On Raspberry Pi OS specifically: `Storage=` changes need (a) an admin-tier `journald.conf.d/` drop-in, not a base-file edit, because of the vendor's volatile-storage drop-in, and (b) `sudo journalctl --flush` after the config change to activate it immediately rather than waiting for the next boot. And: check `df` before assuming a persistent journal will actually retain anything — `SystemKeepFree`'s default floor can silently make "persistent" storage functionally empty on a nearly-full disk.

**Addendum (same day, ~2hrs later): a fourth outage happened live during this same investigation**, and likely found the actual root cause. Right after the journald fix above, the Pi dropped off the network again (SSH/Tailscale/LAN all unreachable) — confirmed via physical console access (`Ctrl+Alt+F2` to a text VT, since the desktop's terminal shortcut was also unresponsive with no mouse available) that the kernel and login were fully healthy, but `ip a` showed `wlan0: <NO-CARRIER,...,DORMANT>` — no IP, no link, WiFi radio up but not associated with any AP. `journalctl -k` had nothing from the actual drop (no disassociation/reset event logged at the kernel level), which pointed at a silent failure mode rather than a driver crash.

**Root cause found: WiFi power-save was on** (`iw dev wlan0 get power_save` → `Power save: on`, live) — a well-documented `brcmfmac` (this Pi's onboard Broadcom WiFi chip) failure mode: the radio drops to a low-power state it doesn't reliably wake from, silently going to no-carrier with no clean disconnect logged, which matches every symptom seen across all 3-4 outages (no kernel disassociation event, hardware watchdog never fired since the OS itself stayed healthy, only the WiFi layer died). Fixed at two levels: `sudo nmcli connection modify Badve 802-11-wireless.powersave 2` (2=disable, persists in the `Badve` connection profile — the only WiFi profile that exists on this box, so this alone covers all current real usage) + `nmcli connection up Badve` to apply live; **and** added `/etc/NetworkManager/conf.d/wifi-powersave-off.conf` (`[connection]\nwifi.powersave=2`) as a global NetworkManager default, since the per-connection setting alone wouldn't protect a future/recreated WiFi profile (the underlying driver's own default is power-save *enabled*, confirmed via the boot-time `brcmf_cfg80211_set_power_mgmt: power save enabled` kernel log line — NM's per-profile "0/default" doesn't override that). Verified live: `iw dev wlan0 get power_save` → `off` after both changes, `wlan0` stayed `UP`/`LOWER_UP` with its IP throughout, SSH never dropped. **Not yet verified across an actual reboot** — the driver enables power-save at probe time (before NetworkManager applies the profile setting), so ordering *should* work, but this is a prediction, not a measurement, and this session already burned time on exactly this gap once already (see the journald "half fix" above). Check at the next natural reboot: `sudo /usr/sbin/iw dev wlan0 get power_save` should read `off`; if it reads `on`, the NM-level fix isn't reaching the driver in time and a boot-time enforcement path is needed instead.

**Also checked, ruled out as a cause (corrected from an earlier wrong read this same session)**: WiFi regulatory country looked mismatched — `raspi-config nonint get_wifi_country` → `IN`, correctly written into the kernel boot cmdline (`cfg80211.ieee80211_regdom=IN`), but live `iw reg get` showed `phy#0: country 99: DFS-UNSET`. Initially misread this as "more conservative power/channel limits" — wrong: the actual `phy#0` capability block has no `NO-OUTDOOR`/`DFS`/`NO-IR` restrictions and includes channel 14 and wide 5GHz spans, i.e. it's *more* permissive than a real country domain would be, not less. FlareSolverr's Cloudflare challenge for 1337x verified solving end-to-end; Prowlarr's Torznab endpoint verified `200` with real (unmasked, pulled from Sonarr's sqlite db) credentials.

**Problems**: root cause needed peeling two layers that looked identical from the error message alone — Radarr's own outbound IPv6 attempt failing (`SocketException: Resource temporarily unavailable`) is a different mechanism from FlareSolverr's stale baked-in `resolv.conf`, even though both manifest as "can't reach this HTTPS host." Quadlet's `DNS=` key sidesteps the whole bug class by making DNS explicit and boot-state-independent — worth using on anything added to this stack going forward, and Quadlet's rootless `podman-user-wait-network-online.service` ordering (auto-injected, confirmed via `quadlet -dryrun -user`) is the correct rootless-safe way to order against network readiness, not a hand-rolled `network-online.target` dependency.

## 2026-08-04 — Qwen3.5-9B vision benchmarked, GPU hallucination bug found and root-caused, filed upstream (openvino#37223)

**Goal**: extend the same-day Qwen3.5-9B OpenVINO eval to a full benchmark including vision (image understanding), not just text.

**Changes**: rewrote `~/LocalAI/test_ov_qwen.py` to benchmark both text-only and vision prompts through one `VLMPipeline` instance (5 timed runs + 1 warmup each, `PerfMetrics` aggregation — same methodology as `openvino-test/benchmark.py`), using `docs/images/architecture.png` (this repo's own architecture diagram) as a real, content-verifiable test image. **Results**: text-only GPU throughput 10.30 ± 0.28 tok/s (TTFT ~447ms), vision GPU throughput 10.20 ± 0.20 tok/s (TTFT ~10.2s — the vision-encoder pass dominates time-to-first-token, as expected). Numbers alone looked like a clean pass. **They weren't** — see Problems.

**Problems (the actual finding)**:
- **GPU vision output is hallucinated, not just imprecise.** Asked to describe `architecture.png` (a flowchart with named boxes and labeled arrows), GPU output described "a grid of identical-looking boxes... woven fabric... soil sample... filter media" — content bearing no relation to the real image. No crash, no exception, well-formed grammatical text — a silent-correctness bug, the kind that survives a "did it crash?" check. Caught only because the test image's content was known ahead of time and manually compared against the response.
- **Isolated via CPU rerun**: same model, same image, same prompt, on CPU — near-perfect description (correct box names, correct port numbers 8000/8080/8081/3000, correct arrow labels). Confirms GPU-specific, not a preprocessing bug (image-loading code double-checked against the official `openvino.genai` sample, matches exactly).
- **Standard GPU-accuracy workaround failed differently than expected**: `INFERENCE_PRECISION_HINT=ov.Type.f32` OOM-killed the process during model *compilation*, before any generation (confirmed via `journalctl -k`), on this 15Gi UMA box. Blanket full-precision GPU inference isn't viable here regardless of whether it would have fixed the accuracy issue.
- **Root-caused, not just reported.** Found a closed precedent for the same failure-mode *class* on a related model: [openvino#33491](https://github.com/openvinotoolkit/openvino/pull/33491)/[#33880](https://github.com/openvinotoolkit/openvino/pull/33880), "[GPU] Fix accuracy issues for Qwen2.5-VL-3B-instruct" — FP16 overflow in the vision-merger's SwiGLU block propagating `NaN` through RMSNorm, fixed via a targeted graph transformation (`IncreasePrecisionForQwenVLMerger` in `increase_rms_input_precision.cpp`) that pattern-matches Qwen2.5-VL's specific merger op sequence and upconverts just that slice to f32. **Checked directly against our exported IR** (`grep -c` on `openvino_vision_embeddings_merger_model.xml`): zero `Swish` ops, zero `RMS` ops anywhere in the graph — the pattern-matcher's required ops don't exist in this model's merger at all. Qwen3.5's merger uses MVN (not RMSNorm) and GELU with no SiLU/Swish gating — a structurally different graph (consistent with `optimum-intel` treating `Qwen3_5VisionEmbMergerPatcher` as a separate class from the Qwen2.5-VL/Qwen3-VL patchers). The existing fix cannot cover this model; confirmed by direct evidence, not inference.
- **Searched thoroughly for an existing report before filing** (multiple query phrasings across `openvinotoolkit/openvino`, `openvinotoolkit/openvino.genai`, and the model's own HF discussion board). One close-sounding hit turned out unrelated on inspection: openvino.genai#3809 ("Fix vision embeddings processing in chat mode for linear attention", already merged, already in the nightly used here) only touches the `start_chat()`/chat-history code path — our reproduction is plain single-shot `generate()`, which never enters that path. The one open HF discussion on the model page is a different bug entirely (stale `openvino-genai` build missing `qwen3_5` registration, Windows/Arc B580). Found nothing matching this symptom.
- **Filed [openvino#37223](https://github.com/openvinotoolkit/openvino/issues/37223)** with full repro code, side-by-side GPU/CPU output, the f32-OOM finding, and the IR-grep evidence — plus the AI-assistance disclosure their [`AI_USAGE_POLICY.md`](https://github.com/openvinotoolkit/openvino/blob/master/AI_USAGE_POLICY.md) requires (checked this policy first: AI-assisted contributions are explicitly allowed, disclosure is mandatory once "meaningful," fabricated claims are grounds for immediate closure — so the report only states what was actually run and verified, separate from what's inferred).

**Lessons**: a throughput benchmark that doesn't check output content against known-correct answers can look completely clean while being wrong — "10.20 tok/s, no crash" said nothing about whether the vision path actually worked. For future VLM eval work here, use a test image with verifiable ground truth (not a generic stock photo) so a bad response is recognizable, not just plausible. Separately: grepping an exported OpenVINO IR's `.xml` for op-type names is a fast, concrete way to check whether a known upstream fix's pattern-matcher covers a given model, without needing to build anything or add instrumentation — useful for this project's future OpenVINO troubleshooting generally.

**Next steps**: `openvino#37223` is unowned so far — check back for maintainer response. No wrapper yet routes vision prompts to CPU / text prompts to GPU (the practical workaround) — would need to land in whatever ends up serving this model (see the OVMS discussion from earlier today, not yet implemented as a script). The Gradio VLM chat demo gap identified in openvino.genai (no official web GUI sample, CLI-only) is still an open, unclaimed contribution opportunity if picked up later.

## 2026-08-02 — OpenVINO Model Server (OVMS) stood up to serve Qwen3-8B through Open WebUI

**Goal**: get the OpenVINO-benchmarked Qwen3-8B model actually usable as a chat model in Open WebUI, not just reachable via one-off Python scripts.

**Changes**: pulled `docker.io/openvino/model_server:latest-gpu` via podman and launched it (`ovms-qwen3-8b`, port 8084) pointed at the already-downloaded `qwen3-8b-int4-ov` IR directory, `--task text_generation --target_device GPU --reasoning_parser qwen3 --tool_parser hermes3`. Added `http://localhost:8084/v3` as a fourth OpenAI-compatible connection in Open WebUI.

**Results**: confirmed working end-to-end with a real chat completion (`curl` against `/v3/chat/completions`, correct `reasoning_content`/`content` split once given enough `max_tokens` to reach the closing `</think>` tag — see Problems). Verified via direct source inspection (not just observed behavior) that Open WebUI's backend now correctly reads all four connection URLs including OVMS.

**Problems**, each a real deployment snag with a concrete fix:
- **SELinux volume labeling** silently caused `Permission denied` reading the mounted model files — Fedora podman needs the `:Z` relabel flag on the volume mount (`-v ...:/models/qwen3-8b:ro,Z`), not just `:ro`.
- **IPv6 localhost resolution breaks podman's rootless port forwarding**: `curl http://localhost:8084/...` failed with "Connection reset by peer" because `localhost` resolved to `::1` first and the `pasta` forwarding helper only handles IPv4; `http://127.0.0.1:8084/...` worked immediately. Worth remembering for any future podman-hosted service on this box.
- **The `qwen3` reasoning parser can't split output cut off mid-thought** — a small `max_tokens` budget (50) meant generation stopped inside the `<think>` block before reaching `</think>`, so the parser had nothing to split on and dumped everything into `content` as a fallback. This is a known upstream behavior (`vllm-project/vllm#35221`), not an OVMS misconfiguration — confirmed correct behavior once `max_tokens` was raised to 500.
- **Open WebUI ignores `OPENAI_API_BASE_URLS` after first-ever startup.** Recreating the container with an updated env var had *zero effect* — Open WebUI persists its connection list in its own sqlite DB (`config` table, `openai.api_base_urls`/`openai.api_keys`/`openai.api_configs` keys) once a data volume has prior state, and the env var is only a seed for a brand-new volume. Traced this by reading `open_webui/routers/openai.py` and `open_webui/models/config.py` directly inside the container rather than guessing - `get_openai_runtime_config()` does a fresh DB read every call (no caching layer), so the fix was a direct `UPDATE` on the `config` table's `openai.*` rows, not another container recreation.
- A `port already in use` error on 8083 turned out to be `metube` (already using that port), not a stale process - moved OVMS to 8084 instead of debugging a phantom conflict.

**Lessons**: for any containerized app with persistent state, check whether config is DB-backed before trusting an env-var change to take effect - `podman inspect`/`podman exec` plus reading the actual source inside the container settled this definitively where behavioral guessing (log-watching, restart-and-hope) was going in circles. `127.0.0.1` over `localhost` is the safer default when scripting against rootless-podman-forwarded ports.

**Follow-up same day: two more real bugs found once actual chat use started.**

1. **Same IPv6 issue, different code path.** The model picker worked (confirming the DB fix above), but sending an actual message got "Server Connection Error" - `open-webui`'s log showed `[Errno 104] Connection reset by peer` on the *generate* call specifically, even though the *list-models* call to the same host had just succeeded. Reproduced directly: `curl http://localhost:8084/...` (IPv6 `::1` first) resets on a streaming POST; `curl http://127.0.0.1:8084/...` streams fine. Fixed by rewriting all four connection URLs in the `openai.api_base_urls` DB config from `localhost` to `127.0.0.1`. Confirmed the fix needs no restart - `Config.get_many()` does a fresh DB read every call (verified via reading `open_webui/models/config.py` directly), so a raw DB `UPDATE` takes effect immediately.

2. **Thinking mode was silently eating 40-110s per response.** Real requests through Open WebUI were taking 38-107s each (measured via `ovms_graph_processing_time_us` after enabling `--metrics_enable` on the OVMS container - it wasn't on by default). Root cause: Qwen3-8B is a genuine hybrid thinking model (see the entry above on this) and Open WebUI sends its full tool-declaration set with every request, so every reply paid for a full `<think>...</think>` pass over a large prompt before any visible content. Verified the standard Qwen3 fix (`chat_template_kwargs: {"enable_thinking": false}` in the request body) actually works through OVMS: a matched curl test dropped from the 40-110s range to **1.3s**. Made it Open WebUI's default for this model by setting the `model` table's `params` column to `{"custom_params": {"chat_template_kwargs": {"enable_thinking": false}}}` - found this exact mechanism by reading `apply_params_to_form_data()` in `open_webui/utils/middleware.py` rather than guessing at Open WebUI's UI. Confirmed via real Open WebUI usage afterward: average dropped to **~9.5s/request** (metrics-measured, not estimated) - not as fast as the bare curl test, so the tool-declaration payload itself is still real overhead, but roughly 8x faster than before.

**Lessons (additional)**: the same root cause can hit different code paths at different times - fixing the model-list call didn't fix the generate call, because they're separate request flows through the same IPv6-resolution bug. When a fix looks incomplete, check whether the *other* thing that uses the same host/config is a genuinely separate code path before assuming the first fix failed. Also: don't guess at a web UI's config mechanism by clicking around - reading the actual backend source (`grep` for how a param name is consumed) found the real mechanism (`model.params.custom_params`) faster and more reliably than trial-and-error through the Admin Settings UI would have.

**Next steps**: `start-qwen3.sh` (production llama-server) is currently stopped (stopped earlier this session to free RAM) - restart it if the usual 4B/Gemma models are wanted alongside OVMS. The ~9.5s/request floor (vs 1.3s bare) suggests the tool-declaration payload size is now the dominant remaining cost - worth investigating per-model tool visibility restrictions in Open WebUI if faster responses are wanted.

## 2026-07-30 — Documented the Podman-over-Docker rationale (retroactively, no re-litigation)

User asked why Podman was chosen for Open WebUI/Open Terminal over Docker; no prior journal entry recorded an explicit decision, so it was never actually debated in-session - Podman was simply the starting choice both container scripts were built on (`start-open-webui.sh`, `start-open-terminal.sh`, see SETUP.md). Capturing the reasoning now so it isn't lost:

- **Fedora default**: Podman ships as Fedora's default container engine; Docker isn't installed out of the box, so Podman was the path of least resistance rather than an extra package to add.
- **Rootless by default**: both containers already run rootless, consistent with the general footprint/privilege-conscious posture used elsewhere (the `slim` image tag, loopback-only binding for `open-terminal`'s port 8000).
- **No daemon**: Podman's fork-exec model means no long-running root `dockerd` on a box that's also serving an LLM and is reachable over Tailscale - smaller attack surface than a persistent root daemon.
- **Docker-CLI compatible**: the scripts use standard Docker-style flags (`--network host`, named volumes, `-p 127.0.0.1:8000:8000`) under `podman run`/`podman start`, so there was no real switching cost versus Docker.

No action taken - this is a documentation-only entry, nothing about the running containers changed.

**Applied a second patch**: wrapped the body of `server_prompt_cache::load()`'s state-restore block in the same `try { ... } catch (const std::exception & e) { SRV_ERR(...); return false; }` pattern - this file already had a precedent for this exact style (a `catch (const std::bad_alloc & e)` a few lines above it, for a different failure mode). Rebuilt, restarted (new PID, healthy). This is now two local patches on top of upstream, both logged here and in memory for reapplication after any `git pull`.

**Still not fully proven safe** - two call sites down, but `get_available_slot()`'s `prompt_clear()` (line 1628, the fallback when `prompt_load()` returns false) hasn't been exercised yet under a real device-lost condition, and there could be other call sites elsewhere in the codebase with the same pattern that haven't been hit yet. The productive path forward is the same as before: keep the patches in place, watch for the next real occurrence, patch whatever unguarded call site turns up next.

**21:48 - both patches fully validated against a real, live device-lost event. Server survived.** A genuine new fence timeout fired on the twice-patched server (PID 24258, confirmed via a fresh, non-replayed timestamp in `gpu-fence-alerts.log`: 21:47:58). The Vulkan device went permanently lost for that process (expected - a lost device doesn't self-heal without a fresh Vulkan context), and every subsequent request cleanly failed with `decode() failed: vk::Device::waitForFences: ErrorDeviceLost` / `vk::Queue::submit: ErrorDeviceLost`, logged via both patches firing repeatedly and correctly on dozens of consecutive requests (`prompt_save() failed: ...`, `failed to restore state: ...`, `failed to load prompt from cache`) - **and the process stayed alive throughout**, serving clean HTTP 500s instead of crashing. Restarted afterward (routine - a lost Vulkan device needs a fresh process to get a working GPU context again; the patches prevent the crash, they don't revive the device) and confirmed normal generation resumed (`curl` "capital of France" -> `Paris`).

**Net effect of both patches**: a fence timeout now costs a temporary run of 500 errors until someone notices and restarts, instead of an unannounced full process crash (previously: silent outage until the next `curl`/UI check revealed the server was gone). **Update, 21:58 - likely root cause found (not just the crash symptom) via upstream research.** Pushed back on "we still don't know why this actually happens" - the two patches above only change how the server fails, not why the iGPU's fence times out at all. Searched for prior art: `i915`/Vulkan-compute fence timeouts on integrated GPUs turn out to be a recognized class of bug, not something specific to this machine - multiple open `llama.cpp` issues describe the same `Fence expiration time out` -> `GPU HANG` -> `vk::DeviceLostError` chain on other Intel iGPU generations (Meteor Lake, Arrow Lake, Arc iGPU: [#20201](https://github.com/ggml-org/llama.cpp/issues/20201), [#16684](https://github.com/ggml-org/llama.cpp/issues/16684)).

The most useful match was [#21724](https://github.com/ggml-org/llama.cpp/issues/21724) - an **identical failure chain on an AMD APU** (Renoir gfx90c, also integrated/shared-memory), with a validated root cause: the Vulkan backend batches up to 100 compute-graph nodes into a single GPU submission (`ggml-vulkan.cpp`, `max_nodes_per_submit`); on an integrated GPU this accumulated work can take long enough that it exceeds the kernel driver's hang-detection timeout (AMD's `amdgpu.lockup_timeout`, i915's fence-expiration equivalent here), and the kernel resets the GPU thinking it's actually stuck - a false-positive hang, not a real one. The validated fix there was reducing the per-submission node count to 1.

Checked this checkout's `ggml-vulkan.cpp` (line 6176-6182): `GGML_VK_MAX_NODES_PER_SUBMIT` already exists as an env var (default 100, the same default that caused the AMD crashes), no rebuild needed to test it. **Set `GGML_VK_MAX_NODES_PER_SUBMIT=1` in `start-gemma-e4b.sh`** (exported before the `exec`, commented with the reasoning and the upstream issue link) and restarted. Quick check: generation speed unaffected (8.05 predicted tok/s on a short completion, in line with the ~9-9.8 tok/s documented baseline) - matches the AMD issue's own finding of no performance penalty from this change.

**Update, 22:03 - user asked "check now realtime, got timeouts" - investigated, found the alert log was stale again, but turned up a real third bug.** `gpu-fence-watch.service` had restarted *again* (22:00:22) and replayed old PIDs (20696, 22242, 24258, 25063) into `gpu-fence-alerts.log` as duplicates - none of that was new. Cross-checked with the raw kernel ring buffer (`dmesg -T`, immune to journald's replay issue since it reads the kernel's own buffer directly) - zero fence lines in the current window. So no evidence the fence timeout itself recurred since the mitigation went live.

However, found a genuinely new, real crash: PID 25063 (running with both crash-patches, but *without* the node-per-submit mitigation - that only applied to the next restart) hit a real device-lost error at 21:54:04 (visible in Open WebUI's own error log), survived it thanks to the patches, then **crashed anyway at 21:58:16 when I sent it SIGTERM to restart for the mitigation test** - a coredump, not a graceful shutdown. Backtrace: `llama_context::~llama_context()` -> `ggml_backend_vk_free` -> `ggml_vk_cleanup` -> `ggml_vk_synchronize` - the *shutdown* path also makes an unguarded Vulkan call ("wait for any pending command buffers to finish" before freeing), and once the device is already lost, that throws too, uncaught, straight out of a destructor. A **third** unguarded call site, this time not in request handling but in teardown - meaning any restart of an already-broken server (which is exactly the recovery procedure used all day) could itself crash instead of exiting cleanly.

**Patched `ggml_vk_cleanup()` directly** (`ggml/src/ggml-vulkan/ggml-vulkan.cpp`, line ~15410) - wrapped its `ggml_vk_synchronize(ctx)` call in `try { ... } catch (const vk::SystemError& e) { GGML_LOG_WARN(...); }`, matching this file's own existing exception-handling convention (`catch (const vk::SystemError& e)` is already used at several other call sites in the same file). This is backend-level code (not server-specific), so the fix benefits any consumer of `ggml-vulkan`, not just `llama-server`. Rebuilt, restarted - ended up with two `llama-server` processes briefly (the `pkill` in the restart sequence didn't actually kill the prior one; cleaned up manually, confirmed via `ss -tlnp` which PID actually held port 8080). Verified generation still works post-patch (`Paris`).

**Current state, 22:03: three local patches + one trial mitigation, all active on PID 28220:**
1. `tools/server/server-context.cpp` - `server_slot::prompt_save()` catches device-lost instead of crashing.
2. `tools/server/server-task.cpp` - `server_prompt_cache::load()` catches device-lost instead of crashing.
3. `ggml/src/ggml-vulkan/ggml-vulkan.cpp` - `ggml_vk_cleanup()` catches device-lost during shutdown instead of crashing.
4. `GGML_VK_MAX_NODES_PER_SUBMIT=1` env var - trial fix for the fence timeout itself (still unconfirmed over time).

All three patches are local-only, unsubmitted, will not survive a `git pull`.

**This is a trial, not a confirmed fix** - the fence timeouts are intermittent (roughly hourly during real use, per today's 4-5 confirmed occurrences), so this needs real usage over a comparable window to know if it actually reduces/eliminates them, not just a synthetic smoke test. If fence timeouts stop (or become much rarer) going forward, this is very likely the actual root cause and fix. If they continue at the same rate even with `max_nodes_per_submit=1`, that specific theory is ruled out and the two crash-prevention patches above remain the fallback safety net regardless. Keep the two `prompt_save`/`prompt_load` patches in place either way - they're a legitimate hardening fix independent of whether this turns out to be the root cause.
